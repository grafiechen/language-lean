# Language Lean 项目概要

> 文档状态：需求、架构与功能基线  
> 当前阶段：日语 Web 版 MVP 规划  
> 更新日期：2026-09-11

## 1. 项目背景

Language Lean 是一个配合纸质单词本使用的个人语言学习工具。

项目当前首先解决日语学习中的一个具体问题：有些单词看到文字时认识，但在真实听力中听到发音时不能及时识别。这类词在本项目中称为“耳词”或“假生词”。

纸质单词本继续承担书写、整理和视觉记忆；本系统主要承担发音生成、听觉回忆、复习调度和耳词强化，不试图在第一版替代完整的语言教材或纸质学习流程。

## 2. 产品目标

第一阶段的核心目标是建立以下闭环：

```text
录入日语单词和例句
→ 生成并保存高质量 TTS
→ 隐藏文字播放单词
→ 用户回忆词义
→ 显示答案
→ 用户选择 × / △ / ○
→ 系统安排下次复习
→ 听觉薄弱词进入耳词池
```

长期目标是在相同账户、词库和复习基础设施上，逐步增加文字背词、词形变化、造句训练和其他语言。

## 3. 第一版范围

### 3.1 账户与权限

- 系统支持多账户。
- 保留用户注册能力，但第一版关闭公开注册入口。
- 第一版账号仅由管理员在后台创建。
- 角色暂定为 `ADMIN` 和 `USER`。
- 普通用户只能访问自己的个人数据，以及已发布的系统词典和用户贡献词条。
- 管理员可以创建、启用、禁用和删除账号，并管理系统配置、词典审核和用量。
- 管理员默认不查看用户的具体学习内容。
- 同一账户后续可以在多个设备上使用并同步进度。

### 3.2 语言配置

- 第一版只实现并启用日语 `ja-JP`。
- 前端不得硬编码可用语言列表。
- 前端从后台接口获取当前启用的语言及其功能入口。
- 页面顶部保留语言上下文区域；只有后台启用多种语言后，才提供实际切换能力。
- 当前语言决定单词本、词性、训练入口、TTS配置和学习进度范围。
- 每个单词本只属于一种学习语言，不在同一个单词本中混合语言。
- 后续语言如果无法与日语共用特定功能，可以使用独立语言模块实现。

### 3.3 单词与例句管理

第一版支持：

- 手动逐个创建或引用词条。
- 使用 CSV 批量导入个人学习条目。
- 查看、修改和删除个人学习条目。
- 检测重复学习条目。
- 为词条填写或引用一个或多个例句。
- 分别生成单词和每条例句的音频。

个人学习条目不保存一份独立的系统词典内容，而是引用一个系统词典条目、公开用户贡献词条，或用户自己的未解析词条。释义、读音、标准例句等内容来自被引用的词典条目；用户标签、笔记、复习状态和耳词状态属于用户自己的数据。

CSV 基础格式暂定为：

```csv
該当,がいとう,符合,N2
```

CSV 字段的最终细节仍需在导入模块开发前确认。

基础信息包括：

- 单词或表达。
- 发音标注；日语第一版对应假名。
- 中文释义。
- 所属单词本。
- 语言。
- 系统词性。
- 自定义标签。
- 例句及例句释义。

### 3.4 分类与标签

系统分类和自定义标签必须分开。

系统分类会影响后续训练能力。日语计划支持：

- 名词。
- 动词：一类、二类、不规则。
- 形容词：い形容词、な形容词。
- 副词。
- 助词。
- 接续词。
- 表达及其他类型。

自定义标签只用于用户整理，例如：

- N1、N2。
- 工作、新闻、易错。
- 纸质本页码或章节。

第一版需要保存这些分类信息，但动词和形容词变形训练属于后续迭代。

### 3.5 听觉测试

基础交互为：

```text
进入测试
→ 页面不显示答案
→ 自动播放单词的主要读音
→ 用户进行回忆
→ 点击“显示答案”
→ 显示单词、假名、中文释义和例句
→ 用户选择 × / △ / ○
→ 自动进入下一题
```

评分含义：

- `×`：完全没有听出来。
- `△`：模糊、反应较慢或主要依靠猜测。
- `○`：能够较快、明确地识别。

测试页面还需要提供重新播放能力。答案显示前不得通过文字、假名或其他信息泄露答案。

第一版同时提供例句音频。例句音频不默认播放；用户点击哪个音频，就只播放哪个音频。单词音频与例句音频相互独立。

一个词条可以有多个读音。普通测试默认播放主要读音；耳词训练可以轮播多个读音。轮播只属于展示和训练内容，不创建额外学习状态。

### 3.6 遗忘曲线

- 系统根据每次 `× / △ / ○` 使用 FSRS/DSR 自动安排下一次复习。
- FSRS 状态只属于“用户 + 个人学习条目”，不属于系统词典。
- `×` 和 `△` 通常会缩短复习间隔，连续 `○` 通常会延长复习间隔。
- 第一版评分映射暂定为：`× → Again`、`△ → Hard`、`○ → Good`；暂不增加 `Easy` 按钮。
- 每次复习必须保留复习事件、评分、复习前后状态、算法版本和下次复习时间。
- 目标保留率、初始学习步骤和 FSRS 具体版本在调度模块开发前确认。

### 3.7 耳词池

- 听觉测试选择 `×` 或 `△` 时，单词自动进入耳词池。
- 用户也可以手动将单词加入耳词池或取消手动重点状态。
- 耳词池提供独立训练入口。
- 耳词不会因为连续几次 `○` 被直接删除。
- 耳词仍由遗忘曲线调度：薄弱时高频复习，稳定后进入低频保持；以后再次答错时恢复高频复习。
- 耳词仍使用同一份 FSRS/DSR 状态；多读音轮播不创建多份状态。
- 耳词历史和复习记录始终保留。

### 3.8 同步与本地使用

- 客户端保留本地词典引用、个人学习状态和音频缓存，以支持快速访问和后续离线能力。
- 打开某个单词页面时，只同步当前单词及其相关内容，不自动全量同步。
- 页面提供手动同步按钮；手动同步作用于当前账户的全部个人数据。
- 音频按单个文件独立检查和更新，不进行全库缓存失效。
- JSON 备份至少包括词典引用、用户词条、例句引用、分类、标签、复习状态、耳词状态和音频版本信息。
- 需要支持JSON导出，并计划支持从JSON恢复。

### 3.9 用户贡献词典

普通用户可以创建系统词典中不存在的基准词条。用户贡献词条使用与系统词典相同的内容结构，但必须记录创建者、来源和审核状态。

用户创建后默认进入：

\`\`\`text
PENDING_REVIEW
\`\`\`

审核通过后才能被其他用户搜索和引用；创建者本人在审核期间可以继续使用。用户贡献词条支持公开、私有、待审核、弃用和封禁状态。

用户个人标签、笔记、学习记录和私人例句不因词条公开而自动公开。

## 4. TTS需求

### 4.1 当前服务

- 第一版使用 Google Cloud Text-to-Speech 的 Chirp 3 HD。
- 当前语言为日语 `ja-JP`。
- 每种语言分别配置TTS服务商、模型、语言代码和固定默认声音。
- 第一版日语只使用一个固定声音，不为每个用户生成不同音色版本。
- TTS只能由服务端调用，客户端不能获得Google服务凭据。

### 4.2 生成对象

- 单词音频。
- 每条例句的独立音频。
- 后续可以增加搭配、变形和其他训练音频，但不属于第一版。

### 4.3 音频版本

每个音频文件拥有独立版本。修改或重新生成某个音频时：

- 只增加该文件的版本。
- 不影响同一单词的其他例句音频。
- 不影响其他单词。
- 新文件上传成功后才切换当前版本。
- 新版本失败时旧版本继续可用。

音频需要记录：

- 所属语言。
- 服务商、模型和声音。
- 生成文本或文本哈希。
- 独立版本号。
- 文件哈希。
- 对象存储路径。
- 生成状态。

### 4.4 保存原则

```text
Spring Boot调用Google TTS
→ 接收生成结果
→ 立即上传Cloudflare R2
→ 上传成功后保存音频元数据
→ 不在Oracle服务器长期保留MP3
```

## 5. Cloudflare存储与托管

### 5.1 R2用途

计划使用两个逻辑隔离的存储空间：

```text
音频存储：单词和例句MP3
私有备份：PostgreSQL备份文件
```

- 音频生成后立即进入R2。
- PostgreSQL定时导出、压缩并备份到私有R2。
- 公开音频与私有数据库备份不能共用访问权限。
- 所有bucket共享Cloudflare账户的免费额度，并非应用内每个用户各有10GB。
- 当前R2 Standard免费额度为每月10 GB-month存储、100万次Class A操作、1000万次Class B操作，出口流量免费；价格和额度上线前需再次核对。

### 5.2 前端托管

- Vue构建产物计划部署到Cloudflare Pages。
- Pages负责前端静态资源和全球分发。
- 前端不必占用Oracle实例资源。
- API和音频使用独立子域名。

Web和未来App需要复用：

## 9. 扩展原则

- 通用能力保持语言无关：账户、单词本、单词、例句、音频、复习、耳词、同步和备份。
- 日语专属能力独立组织：假名、日语词性、动词类别和形容词类别。
- 新语言优先复用通用能力；确实无法通用的规则采用独立实现。
- 不为了假设中的未来语言提前构建复杂通用框架。
- 不把TTS实现细节散落在训练页面中。
- 不把Web存储实现写入核心复习逻辑。
- 后端API既服务于Web，也必须能被未来iOS和Android客户端使用。

## 10. 当前尚未最终确认

以下事项不阻碍项目骨架和通用基础能力搭建，但应在进入对应模块前确认：

- FSRS 具体版本、默认参数、目标保留率和初始学习步骤。
- 第一版例句的录入和 CSV 格式细节。
- Unicode、空白、假名等书写规范化规则的具体版本。
- PostgreSQL 备份频率、保留周期与加密方式。
- Cloudflare 代理采用 IP 白名单还是 Cloudflare Tunnel。
- 第一版具体的日语 Chirp 3 HD 声音。
- 用户贡献词条审核标准、举报处理和管理员操作细节。

以下事项已经确认：例句不自动播放；多读音有主要读音并支持排序和轮播；重复判定不使用释义和标签；用户贡献词条默认待审核；AI Agent 不纳入当前系统设计。

## 11. 词典底层模型（当前确认版）

### 11.1 基本原则

词典内容分为三类：

~~~text
系统词典条目：全局权威、只读
用户贡献词条：用户创建、审核后共享
个人未解析词条：用户自己创建、默认私有
~~~

系统词典是全局只读知识库。普通用户只能查询、引用和基于词典创建个人学习数据，不能修改系统词典。管理员通过导入、审核、修订和发布新版本维护系统词典。

词典需要区分以下对象：

```text
字符 Character
WordEntry
  written                 // 固定的基准写法
  ├─ Pronunciation[]      // 一个或多个读音
  ├─ Sense[]              // 一个或多个词义
  ├─ GrammarFeature[]     // 词性和语法属性
  ├─ ExampleSentence[]
  ├─ InflectedForm[]      // 活用或派生形式
  ├─ 多词表达与组成关系
  ├─ 词义级词汇关系
  └─ 来源、许可证、质量状态和版本
```

基准词条以一个固定的书写形式为身份。相同书写形式只建立一个基准词条；读音、词义、词性和例句都是该词条下的内容。不同书写形式不因读音或释义相同而合并。

系统词典和用户贡献词典的基准条目唯一键为：

~~~text
language + script + normalized_written
~~~

异体字或其他书写变体如果需要关联，应建立单独条目并使用关系连接，而不是在一个基准词条中保存多个主写法。

复合词（如「今日」「大人」）作为独立基准词条保存自己的读音和含义，同时可以通过组成关系关联「今」「日」等组成单位，不能根据单字读音简单拼接。

### 11.2 读音、词义与排序

同一个基准词条可以有多个读音和多个词义。每个读音和词义至少保存：

~~~text
is_primary
display_order
quality_status
source
version
~~~

is_primary 控制默认展示和播放；display_order 控制页面顺序。常用程度、频率和地区等外部标注单独保存，不直接等同于手工展示顺序。

近义词、反义词、相关词、自动词/他动词等关系绑定到具体词义；如果关系只适用于一个词义，不能只绑定整个词条。

### 11.3 标准例句

标准例句属于系统词典内容，但例句本身是独立实体。例句主要按具体词义分组：

```text
WordEntry
  └─ Sense
      └─ SenseExample
          └─ ExampleSentence
```

一个词义可以有多个标准例句；一条例句也可以关联多个词义，但应设置 `PRIMARY` / `SECONDARY` 关系，默认只在主要词义下展示。

标准例句需要支持：多语言翻译、来源和许可证、难度、正式程度、地区、使用频率、标准音频及独立版本号。用户例句单独存放，不能修改标准例句。

例句录入或导入时完成分词、词形还原和词典匹配，并保存派生结果：

```text
ExampleSentence
  └─ ExampleTokenization
      └─ ExampleToken
          └─ TokenEntryCandidate
```

前端点击例句中的词语时，使用已保存的token和词典ID直接打开词典卡片。分词结果需要记录分析器版本和词典版本；原始例句保持不变。

### 11.4 语言通用核心与语言扩展

通用核心适用于日语、英语和汉语：基准词条、词形、发音、词义、释义、例句、词汇关系、来源和版本。

语言专属内容放在语言扩展中：

- 日语：汉字、平假名、片假名、读音限制、熟字训、五段/一段/サ变/カ变、自动词/他动词、助词和活用。
- 英语：英美拼写、IPA和地区发音、单复数、过去式、过去分词、比较级、不规则形式、及物性和短语动词。
- 汉语：简体/繁体、普通话和方言读音、拼音声调、量词、离合词以及地区用法。

词典语言、文字脚本、发音locale、释义语言和TTS语言分别保存，不使用一个字段混合表示。

### 11.5 规则变形与不规则变形

符合标准规则的词，保存语言属性和规则类别，由统一规则生成变形：

```json
{
  "entryId": "entry_xxx",
  "language": "ja",
  "partOfSpeech": "VERB",
  "conjugation": {
    "mode": "RULE",
    "ruleClass": "GODAN_KU",
    "ruleVersion": 1
  }
}
```

生成的词形记录语法特征和规则版本：

```json
{
  "formType": "TE_FORM",
  "written": "書いて",
  "reading": "かいて",
  "generated": true,
  "ruleVersion": 1
}
```

不符合通用规则的词，明确标记为特例并保存覆盖结果：

```json
{
  "entryId": "entry_xxx",
  "language": "ja",
  "partOfSpeech": "VERB",
  "conjugation": {
    "mode": "OVERRIDE",
    "ruleClass": "GODAN_KU",
    "irregular": true,
    "overrides": [
      {
        "formType": "TE_FORM",
        "written": "行って",
        "reading": "いって",
        "reason": "IRREGULAR"
      }
    ]
  }
}
```

优先级为：词条特例覆盖 → 语言特殊规则 → 通用规则。一个语法形式可以允许多个正确结果，并保存说明、来源和版本。

### 11.6 用户学习数据与系统词典的边界

系统词典和用户贡献词典只提供内容，用户学习域只保存引用和个人状态：

~~~text
UserLearningItem
  user_id
  dictionary_entry_id
  wordbook_memberships
  fsrs_state
  ear_word_state
  review_history
~~~

一个词条可以被多个用户引用；每个用户的 FSRS/DSR 状态完全独立。一个词条有多个读音或多个词义时，仍然只对应一份用户学习进度。读音和词义只影响页面展示、音频选择和例句关联。

### 11.7 查询与例句点击

查询接口统一，但具体分析按语言实现：

```text
输入
  → Unicode规范化和语言处理
  → 精确文字/读音查询
  → 变形还原
  → 文字变体和发音别名查询
  → 模糊匹配
  → 返回候选词条、读音、词义和匹配类型
```

日语搜索支持汉字、平假名、片假名、复杂变形和多音字；英语支持不规则形式和英美拼写；汉语支持简繁、拼音和多音字。

候选优先级为：

~~~text
精准系统词条
→ 精准用户贡献词条
→ 精准个人词条
→ 模糊匹配
~~~

每一层内部使用动态 score 排序。系统词典、用户贡献词条和个人词条的来源优先级不能被模糊匹配分数随意逆转。语言分析和词形还原由应用层完成，PostgreSQL负责索引、候选筛选和排序。

### 11.8 来源、版本和派生数据

原始来源、规范词典数据和派生索引分开保存：

```text
原始来源数据 → 规范词典数据 → 分词/变形/搜索索引/音频
```

导入内容先进入暂存区，经格式校验、去重、冲突检查和管理员审核后发布。相同书写形式的基准条目不重复创建；新读音、新词义和新例句作为同一条目下的待审核补充，不覆盖已有内容。词条、读音、词义、变形和例句都有自己的质量状态。

词典更新不能覆盖用户学习记录。合并、拆分、替换和停用通过迁移关系保持旧ID可追踪。JLPT、HSK、CEFR、频率、地区和语域属于独立标注，不直接写死在词条核心中。

### 11.9 用户贡献词条与个人未解析词条

普通用户可以创建系统词典中不存在的固定书写形式。用户贡献词条与系统词典使用相同的内容结构，但记录创建者、来源、可见性和审核状态：

~~~text
origin_type: USER_CONTRIBUTED
created_by_user_id
visibility
moderation_status
source
license
current_revision_id
~~~

用户创建后默认进入 `PENDING_REVIEW`；审核通过后才能被其他用户搜索和引用，创建者本人在审核期间可以继续使用。已经被别人引用的词条不能硬删除，只能弃用、封禁或迁移。

如果用户只记录了写法而暂时没有读音或释义，可以先建立个人未解析学习项，待补充后再申请成为用户贡献词条。管理员以后可以将用户贡献词条整理为正式系统词条，并通过迁移关系保留旧 ID 和用户学习进度。

### 11.10 字符与编码

字符层独立于词典词条层，用于保存 Unicode 码点、字符读音、部首、笔画、简繁关系、日语音读/训读及其他字符属性。

数据库、JSON、HTTP 和导入后的统一存储使用 UTF-8。当前不把 Unicode 新版本升级作为业务功能；保留原始文字、字符码点和规范化搜索键即可。编码支持与字体显示分开处理，数据库能保存字符不代表所有客户端字体都能显示该字符。

### 11.11 标准对齐原则

项目采用“参考标准的结构，不强求完整标准认证”的策略：

- ISO 24613-1:2024（LMF Core）作为词条、读音、词义和词形分层的主要参考。
- ISO 24613-2:2020（MRD）作为机器可读词典和导入模型的参考。
- ISO 24613-6:2024 作为词法、句法和语义关系的参考。
- ISO 639 用于语言代码。
- ISO 15924 用于文字脚本代码。
- `ja-JP` 作为当前发音/TTS 的 BCP 47 locale；它不替代语言代码和脚本代码。
- ISO 1951 主要用于词典条目的呈现原则，不直接决定数据库表结构。

## 12. 第一阶段完成标准

第一阶段可交付版本至少应满足：

- 管理员可以创建和管理账户。
- 用户可以创建单词本和个人学习条目。
- 用户可以引用系统词典，也可以创建待审核的用户词条。
- 系统能按固定书写形式执行词条去重，已存在时默认跳过且不覆盖。
- 词条支持多读音、多词义及主要项和展示顺序配置。
- 听觉测试隐藏答案，自动播放主要读音，支持重播和 `× / △ / ○` 评分。
- 例句音频不自动播放，点击哪个播放哪个。
- 每个用户拥有独立的 FSRS/DSR 进度和复习历史。
- `× / △` 能进入耳词池，多读音轮播不拆分状态。
- 音频能独立版本化并保存到 R2。
- 个人数据能同步和导出 JSON。
- 系统词典、用户贡献词条和个人学习状态的权限边界清晰。

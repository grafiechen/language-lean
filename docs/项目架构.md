## 目录与依赖方向

- frontend/src/pages：Ionic 页面与路由。
- frontend/src/features：业务功能、Pinia 状态，以及词典内容编辑与预览组件。
- frontend/src/core：不依赖 Vue、Dexie 或 HTTP 的复习协议、评分聚合和端口。
- frontend/src/platform/web：Web 存储适配器，当前实现多账号待上传队列的 IndexedDB 分区。
- backend：Java 21 / Spring Boot 模块化单体，一个构建和部署单元。
- backend 的业务包按 languages、reviews、accounts、dictionary、learning、audio、sync 划分；未实现模块只记录边界，不生成空控制器。
- compose.yml：本地 PostgreSQL 与 API，数据库不映射宿主端口。
- docs：需求与架构依据。

模块内部按需要细分 api/application/domain/infrastructure。业务域不得依赖页面、云 SDK 或 IndexedDB；通过端口接入基础设施。不提前拆微服务或为每个领域创建 Maven 子工程。

## 数据访问约定

业务数据库操作统一使用 Spring Data JPA：Controller → Service（事务边界）→ Repository → Entity。当前语言接口已采用 JPA 实体、复合主键映射、Repository 派生查询和 EntityGraph 关联加载；Controller 不编写 SQL，实体不直接作为 API 响应。

Flyway 负责结构和初始配置迁移，Hibernate ddl-auto=validate 只验证映射，不自动修改生产表结构。后续模块沿用此约定；当前不混用 MyBatis-Plus 或直接 JDBC。

公共发音反馈新增V19迁移，以独立JPA快照保存问题、服务器音频基准和处理版本；用户列表按认证账户隔离，后台生成在事务外执行，失败不误结单。账号注销级联删除本人反馈。后端118项、前端128项与隔离PostgreSQL/Chrome验收通过，见[公共发音反馈与测试](./公共发音反馈与测试.md)。

## 注释约定

- Flyway 迁移为业务表和不直观的关键字段添加 COMMENT ON，说明用途、身份、版本及删除边界。
- Java 类和关键业务方法使用 Javadoc，重点说明职责、事务、权限和幂等行为；JPA 必需的无参构造也说明用途。
- TypeScript 对领域契约、存储适配器和有状态业务方法使用 TSDoc。Vue 模板只在交互目的不明显时注释。
- 注释解释“为什么”和边界条件；简单 getter、框架注解和显而易见的赋值不逐行复述。代码行为变化时必须同步更新注释。

## 当前纵向切片

Flyway V1 初始化日语及 LISTEN_RECALL 配置 → GET /api/v1/languages 查询数据库 → 前端语言区域展示。
公开语言读取、健康检查和 CSRF 初始化；用户名/邮箱登录、当前用户、退出及登录态改密使用服务端 Session Cookie。个人接口必须认证，管理员路径要求 ADMIN 角色。Swagger/OpenAPI 依赖已预留且默认关闭。

账号、角色和登录标识使用 JPA。用户名和邮箱都写入全局唯一的 user_login_identifier，防止一个账号的用户名与另一个账号的邮箱冲突。密码使用带 `{bcrypt}` 算法标识的单向哈希，每次生成独立随机盐；算法标识和盐包含在哈希格式中，便于以后迁移算法。数据库没有明文密码、独立盐列或可逆密钥。

首次管理员由 BOOTSTRAP_ADMIN_USERNAME、BOOTSTRAP_ADMIN_EMAIL、BOOTSTRAP_ADMIN_PASSWORD 三个环境变量共同初始化，密码至少 8 位，且必须同时包含字母、数字和特殊字符；全部留空时不创建账号，缺少任一项则启动失败。仅空库初始化且幂等，不覆盖现有账号，不复活已注销身份。初始账号带 mustChangePassword 标志，首页提供改密表单。普通账号创建、邮件投递、找回密码、禁用和注销已实现，详见账号管理与邮件找回、账号注销与数据清理文档。

第一版核心扩展接口包含 account scope、progress epoch、题型结果、逐次尝试和一次完成事件。Again 重试后 Good 仍聚合为 Again，未通过不能聚合为完成。已接入官方Java FSRS与浏览器一致性实现，以及分组题型队列和自动队尾重试。

IndexedDB的pending/drafts/states均以accountKey开头组成复合键；accountKey由服务端稳定标识与用户UUID构成。acknowledge只清除指定账号指定事件，不能用当前登录名重写旧数据归属。已实现判定、草稿、完成事件及投影的事务缓存、原账号认证补传、冷启动恢复和多设备核对。

## 本地启动

### 后台词典基础管理

- /admin 仅允许 ADMIN 进入；后端所有 /api/v1/admin/** 端点强制角色授权，前端路由保护仅辅助导航。
- 语言配置支持创建、编辑和启停，并带乐观锁版本。新语言默认注册 LISTEN_RECALL 第一版契约；禁用语言不出现在用户词典查询中。
- 基准词条以 UUID 为稳定身份，语言、ISO 15924 书写系统及 NFKC 规范化写法构成唯一键。身份创建后不随内容版本修改，当前不提供改名和合并。
- V3 建立 dictionary_entry 和 dictionary_revision；V4 给 language_config 加编辑版本。已有 V1/V2 不修改，真实数据库可以增量迁移。
- 读音、词义、例句存为schemaVersion=1的类型化JSON快照，通过JPA映射text列。子项均带UUID，顺序即展示顺序，首项为主要项。可选语言标签、译文映射和独立例句出处兼容旧快照；JMdict释义为英语，缺少母语译文明确回退，发音保持学习语言。
- 写法、语言和书写系统属于词条身份；读音、独立发音文本、词性、释义、例句、来源和许可属于版本内容。例句归属词义，例句发音允许为空，不以正文替代。
- 管理员手工录入先保存草稿，再明确确认发布；确认人作为发布人记入历史，当前不要求第二名管理员复核。普通用户投稿使用V14的独立申请及审核版本协议。
- 发布至少填写一个词义；读音允许缺失。草稿保存不改变用户看到的内容，只有完整发布事务提交后才切换公开版。历史恢复先复制为草稿，确认后追加新版本，不改写旧历史。
- 每个修改请求必须携带编辑版本；后端行锁、JPA 乐观锁、草稿基准检查及数据库唯一键防止并发覆盖和重复身份。后台与用户查询均每页 20 条。
- 封禁后用户只能看到词条身份和已封禁标记，不能读取基准内容；管理员可查看历史，但不可继续发布。个人释义、笔记、标签和独立私有词条已开放；解除封禁及公开删除后续实现。
- /dictionary 及 /dictionary/:id 提供登录用户的列表与详情。前端路由按需加载；保存错误和冲突直接提示，未保存编辑离开页面前确认。
- V5 增加词条来源和导入批次。上传文件先以严格 UTF-8 解析并保存规范化暂存快照、SHA-256 与逐条报告；确认前不改公开词典。确认后一次性发布 READY 项，数据库中已有和文件内重复项均明确提示并跳过，不覆盖旧内容。
- V6 增加通用系统字典和可排序选项，首个 `CONTENT_SOURCE` 字典驱动词条编辑页的“内容来源”下拉框。选项可改显示名称、排序和启停；稳定保存值不允许修改，停用不会改写历史词条快照。
- V7 增加开源词典发布登记，保存来源代码、版本、下载地址、源文件 SHA-256、许可和实际导入数量，便于部署后核对基准数据。
- V8增加`wordbook`、`user_learning_item`和`wordbook_learning_item`。同一用户对同一公开词条只创建一份学习条目，多个单词本共享进度；最后关联移除清理学习条目，重置切换`progress_epoch`并清除全部进度和手动重点。V9接入FSRS-6计算及线性完成事件。
- 学习 API 现在提供单词本增删、词条加入/移除、完整重置和 `review-queue` 查询；复习队列只返回公开且到期的词条，已有到期时间的词优先于尚未初始化的词。
- 前端`core/training.ts`实现第一版训练批次协议：每组最多10词，题型按阶段推进，Again自动进入当前阶段队尾，保留全部尝试并在该词完成后聚合最差评分。实际听音页面、离线草稿及逐词上传已接入；耳词模式保留于批次，轮换全部可用读音，共享同一份FSRS。
- 当前上传契约为与来源无关的 schemaVersion=1 JSON，每批最多 10 MB、5000 词，适合后台人工批次。JMdict 全量数据由仓库脚本流式转换成独立 PostgreSQL 初始化 SQL，不受后台上传大小限制；初始化 SQL 幂等插入，不覆盖已有词条或版本。格式与人工验收见《词典导入格式与实际测试》文档。

### 启动步骤

容器预览只需可用的 Docker Engine 和 Compose（Linux 容器）；本机使用 Ubuntu WSL 内的独立引擎，无需 Docker Desktop。Java、Maven、Node 和 Nginx 均在镜像内运行。

1. 根目录复制 .env.example 为 .env，填写本地数据库密码及首次管理员三项配置。
2. 根目录执行 docker compose up --build -d，构建并启动前端、数据库与 API。
3. 首次构建需要下载基础镜像及依赖；docker compose ps 可查看容器状态。
4. 浏览器访问 http://localhost:5173。若端口被其他项目占用，在 `.env` 设置 `WEB_PORT=5174` 后访问对应端口。前端 Nginx 将 /api 代理到内部 api:8080，保持认证同源。
5. GET http://localhost:8080/actuator/health 返回健康状态。

Docker 引擎必须先启动。数据库不公开宿主端口；独立运行 Java 时使用自行准备的 PostgreSQL，并通过 DB_URL、DB_USER、DB_PASSWORD 指定连接。不要将数据库密码写入仓库。

停止与恢复使用 docker compose stop / start；移除容器及网络使用 docker compose down，保留数据库卷。只有确定删除本地全部数据时才使用 docker compose down --volumes。

### Docker 热更新开发

执行 `docker compose -f compose.dev.yml up -d` 会以相同的服务名替换预览容器，继续使用现有 PostgreSQL 数据卷：

- 前端挂载 frontend 源码，Vite 监听 5173，并通过轮询保证 Windows 工作区经 WSL 挂载后仍能触发 HMR。容器每次启动执行 npm ci，依赖严格跟随 package-lock.json；下载缓存保存在独立数据卷。
- 后端挂载 backend 源码。监听脚本按内容指纹检测 src/main 变化，只在变化时执行 Maven 编译；Spring Boot DevTools 检测 target/classes 后重启应用上下文。编译错误不会替换当前已运行的类，修正并再次保存后继续监听。
- 开发端口仍仅绑定 127.0.0.1。宿主机直接执行 npm run dev 时也只监听本机；只有容器命令将 Vite 覆盖为 0.0.0.0，再由 Docker 限制宿主端口。
- 修改 pom.xml 后执行 `docker compose -f compose.dev.yml restart api`；修改 package-lock.json 后执行 `docker compose -f compose.dev.yml restart web`，使容器重新运行编译或 npm ci。执行 `docker compose up --build -d` 可恢复生产式 Nginx/JAR 预览。

## 复习调度与提交实现

- 官方 `java-fsrs:1.0.0` 负责 FSRS-6 计算；学习条目保存当前卡片，独立事件表保存完整尝试、基准状态、结果和参数快照。
- `POST /api/v1/learning/reviews` 处理逐词完成事件，按实际答题时间更新当前进度，重复上传幂等；`GET /api/v1/learning/items/{id}/reviews` 提供最近历史。
- V9 SQL 使用学习条目行锁配合服务事务串行化提交、重置与删除；新代际拒绝旧缓存，删除学习条目级联清除历史。
- 前端 IndexedDB 一次事务保存队列和完成事件；自动与手动补传共用上传器，账号分区和服务器会话校验防止归属混用。听音页面、账号分区音频/内容缓存、静态应用壳和离线账号恢复已接入；联网进入页面及上传前核对多设备变更，未知冲突原记录保留，可重试或明确丢弃依赖链。
- Java 21 容器的测试 JVM 显式加载 Mockito agent，避免依赖运行时自挂载；只影响测试，不进入生产 JAR。

## 检查与构建

- frontend：npm test；npm run build。
- backend：mvn test；mvn package。
- 构建依赖由 Maven BOM 和 package-lock.json 锁定。Maven 可通过 -Dmaven.repo.local 指定缓存路径。
- 部署镜像基于支持 ARM64 的 Java/PostgreSQL 镜像；当前 Compose 仅为本地入口，不包含生产 Nginx、TLS、域名或备份自动化。
